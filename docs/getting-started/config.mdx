Cline configuration lives in two scopes:

- **Global configuration** in `~/.cline/` (applies globally across all Cline applications, including IDE, CLI, and SDK)
- **Project configuration** in `.cline/` (applies only to the current workspace)

## Configuration Directory Layout

Cline stores shared configuration across a few well-known locations. The primary root is `~/.cline/`, with structured app state under `~/.cline/data/`:

```text
~/.cline/
  data/
    settings/
      providers.json           # API keys and provider configuration
      global-settings.json     # Global settings
      cline_mcp_settings.json  # MCP settings
    teams/                     # Team state
    sessions/                  # One folder of messages per session
    db/                        # SQLite databases (sessions.db, cron.db, ...)
    logs/                      # CLI and hub logs
  rules/                       # Global rules
  workflows/                   # Global workflows
  hooks/                       # Global hooks
  skills/                      # Global skills
  agents/                      # Global agent definitions
  plugins/                     # Global plugins (.js, .ts)
  cron/                        # Global cron specs
```

Additional global search paths supported by the code:

```text
~/Documents/Cline/
  Rules/                       # Additional global rules
  Hooks/                       # Additional global hooks
  Plugins/                     # Additional global plugins
  Workflows/                   # Additional global workflows
```

Project-level configuration lives in `.cline/` at your repository root:

```text
.cline/
  rules/                       # Project rules
  workflows/                   # Project workflows
  skills/                      # Project skills
  hooks/                       # Lifecycle hooks
  agents/                      # Project agent definitions
  plugins/                     # Project plugins
```

Notes:

- Global provider settings, global settings, and MCP settings are stored under `~/.cline/data/settings/`.
- Global rules, workflows, hooks, skills, agents, plugins, and cron specs resolve directly under `~/.cline/`.
- Rules, hooks, plugins, and workflows may also be discovered from `~/Documents/Cline/` for compatibility.
- In a project, Cline also reads the older `.clinerules/` layout (rules, plus its `workflows/`, `skills/` and `hooks/` folders), `AGENTS.md` at the project root, and skills in `.agents/skills/`. Globally, it also reads `~/.agents/AGENTS.md` and skills in `~/.agents/skills/`.

## What Goes Where?

- Use **global (`~/.cline/`)** for defaults shared across all Cline applications (IDE, CLI, SDK) on your machine.
- Use **project (`.cline/`)** for team-shared behavior that should travel with the repo.

Commit `.cline/` files you want to share with your team. Keep secrets out of the repo.

## Configure Through the CLI

Use the interactive config UI:

```bash
cline config
```

From there, you can view/edit:

- Settings (global + workspace)
- Rules
- Skills
- Hooks

## Useful Configuration Commands

Use a custom configuration directory:

```bash
cline --config /path/to/custom/config "your task"
```

Or via environment variable:

```bash
export CLINE_DIR=/path/to/custom/config
cline "your task"
```

Open the CLI log file (`~/.cline/data/logs/cline.log`, or the file `CLINE_LOG_PATH` names) when troubleshooting:

```bash
cline doctor log
```

### Context limits

Cap how much text moves between the model and its tools. Values are characters
unless the name says bytes or lines.

| Variable | Default | Governs |
|----------|---------|---------|
| `CLINE_TOOL_MAX_COMMAND_OUTPUT_CHARS` | `48000` | `run_commands` output; beyond this the middle is elided |
| `CLINE_TOOL_MAX_READ_LINES` | `2000` | Lines per `read_files` window |
| `CLINE_TOOL_MAX_LINE_CHARS` | `2000` | Characters per line in reads and search results |
| `CLINE_TOOL_MAX_READ_OUTPUT_CHARS` | `48000` | Characters per `read_files` window |
| `CLINE_TOOL_MAX_SEARCH_OUTPUT_CHARS` | `48000` | `search_codebase` output per query |
| `CLINE_TOOL_MAX_WEB_FETCH_CONTENT_CHARS` | `48000` | Page content kept per `fetch_web_content` request |
| `CLINE_TOOL_MAX_EDITOR_INPUT_CHARS` | `50000` | `old_text`/`new_text` accepted per `editor` call |
| `CLINE_TOOL_MAX_COMMAND_INPUT_CHARS` | `12000` | Length the model is asked to keep each shell command within |
| `CLINE_TOOL_MAX_EDITOR_DIFF_LINES` | `200` | Diff lines in the `editor` result summary |
| `CLINE_TOOL_MAX_COMMAND_PREVIEW_CHARS` | `200` | Command text echoed back in the tool result |
| `CLINE_MESSAGE_BUILDER_MAX_TOOL_RESULT_CHARS` | `50000` | Each tool result forwarded to the model |
| `CLINE_MESSAGE_BUILDER_MAX_FILE_CONTENT_CHARS` | `50000` | Each file attached to a message |
| `CLINE_MESSAGE_BUILDER_MAX_TOTAL_TEXT_BYTES` | `6000000` | Text across the whole request |
| `CLINE_MESSAGE_BUILDER_MAX_ASSISTANT_TEXT_CHARS` | `200000` | Each assistant message |
| `CLINE_MESSAGE_BUILDER_MAX_ASSISTANT_TOOL_MARKUP_CHARS` | `12000` | Assistant text carrying repeated tool-call markup |
| `CLINE_MESSAGE_BUILDER_MIN_OUTDATED_REWRITE_BYTES` | `65536` | Reclaimable bytes before stale file reads are rewritten |

Rules:

- Values that are not positive integers are ignored, and the default applies
- Lowering `CLINE_MESSAGE_BUILDER_MAX_TOOL_RESULT_CHARS` lowers the tool caps with
  it, so output is never trimmed twice; raising a tool cap raises it to match
- `CLINE_MESSAGE_BUILDER_MIN_OUTDATED_REWRITE_BYTES` also accepts `0` to rewrite
  superseded file reads immediately, or `infinity` to leave them in place
- A tool result is re-sent on every later turn of a task, so larger limits cost
  tokens for the rest of that task
- The IDE reads the environment its editor was launched with, which on a desktop
  launch is not your shell's; restart the editor after changing these

In the VS Code extension, the same limits can be set under **Settings → Agent
Limits**, together with tool, ripgrep and hook timeouts, repeated-tool-call
detection, the consecutive-mistake limit and [compaction](#compaction). An env
var set for the editor takes precedence over the setting, and the settings page
marks each field it overrides. Changes apply to the current task once it is idle.

The **Model API** group there applies to every provider:

- **Response timeout** (default 5 minutes): how long a request may wait for the
  model to start responding. A request that times out is retried. Once a
  response starts streaming it is never cut off.
- **Retries** (default 5): how often a request is retried when it fails to
  start, times out, comes back empty or drops before any output. 0 turns
  retries off.

### Tool calls

When the model requests several tool calls in one response, read-only tools
(`read_files`, `search_codebase`, `list_files`, `code_intelligence`, `fetch_web_content`, skills) run
concurrently. Everything else runs in order, and approvals are still asked one at
a time.

| Variable | Default | Governs |
|----------|---------|---------|
| `CLINE_MAX_PARALLEL_TOOL_CALLS` | `4` | Read-only tool calls run at once; `1` runs every call in order |
| `CLINE_PARALLEL_TOOL_CALLS` | `true` | `false` (or `0`, `off`) asks the provider for one tool call per response |
| `CLINE_READ_BEFORE_WRITE` | `true` | Refuse `editor` and `apply_patch` changes to an existing file the agent has not read in this session, or that changed since it last read it |
| `CLINE_REVERT_DETECTION` | `true` | Add a note to an `editor` or `apply_patch` result when the write restores a file to an earlier state from this session, so the agent checks why the later changes were made |
| `CLINE_REVIEW_BEFORE_FINISH` | `true` | In act mode, when a request changed files and the agent answers without tool calls, send it back once with the list of changed files to review them before its final report |
| `CLINE_NESTED_SUBAGENTS` | `false` | Give subagents `spawn_agent` too, so they can start subagents one level deeper. Those cannot delegate further |

With read-before-write on, any successful `read_files` of a file counts, including a line range, and Cline's own edits keep the record current. The record is cleared when older history is compacted and starts empty in a resumed session, so the agent reads files again before editing them. Creating new files and `run_commands` are not checked.

Revert detection keeps a hash of each file's last 20 states, from its content before the first edit onward. It is kept when history is compacted and starts empty with a new task or a resumed session. Writing the same content again, and files that were deleted, get no note.

The review before finishing lists the files whose git status changed since the request started, plus the files `editor` and `apply_patch` wrote (which also covers files outside a git repository). It is asked once per request and costs one more model turn when files changed.

Subagents never ask the user a question, and without nested subagents only the main agent
starts them. Each subagent gets Cline's working rules and environment around the role the
main agent wrote for it, and compacts its own context under the session's compaction
settings.

In the VS Code extension, these settings are under **Settings → Agent Limits → Tool calls**,
and nested subagents under **Agent Limits → Subagents**.
The CLI also takes `--max-parallel-tool-calls <n>`, `--no-parallel-tool-calls`,
`--no-read-before-write`, `--no-revert-detection`, `--no-review-before-finish` and
`--nested-subagents`, and reads `maxParallelToolCalls`, `parallelToolCalls`,
`readBeforeWrite`, `revertDetection`, `reviewBeforeFinish` and `nestedSubagents` from
`global-settings.json`. An env var wins over the flag and the file, and the flag wins
over the file. Values that are not valid (a non-positive or non-integer count, an
unrecognized boolean) are ignored.

### Subagents and agent teams

Both let the main agent hand work to other agents. They differ in whether the main
agent waits, and in how long the helpers live.

| | Subagents (`spawn_agent`) | Agent teams (`team_*` tools) |
|---|---|---|
| Main agent while they work | Waits for the result. Several subagents started in one response run in parallel | Keeps going. A task given with `runMode: "async"` runs in the background, and its result arrives as a new turn for the main agent |
| You while they work | The main agent's turn is busy, so messages queue | You can keep talking to the main agent; a queued message is answered while teammates continue |
| Lifetime | One task. A subagent starts fresh and ends when it reports | A teammate is created once with a role and keeps its conversation across the tasks it is given |
| Communication | Task in, final answer out | The main agent can message one teammate or all of them, check status, wait for runs or cancel them, and track tasks on a shared task list |
| Saved state | Each subagent's messages, under the session | The team (teammates, tasks, runs, messages), restored when the session resumes |
| Approval | Each `spawn_agent` call | Each `team_spawn_teammate` and `team_run_task` call. Status, messages and the task list need none |
| Good for | Focused lookups or edits the main agent needs before its next step | Longer work split into roles that run side by side |

In both cases the helpers run their own tools without asking (in VS Code: read, edit and
web fetch, no terminal), never ask you a question, and each one is a separate model
conversation whose tokens and cost add to the task. Agent teams include subagents.

In the VS Code extension, choose **Settings → Features → Delegation**: Off, Subagents or
Agent teams. Each subagent batch and each teammate run shows a status row with its task,
tool calls, latest tool, tokens and cost. The CLI turns on both except in yolo mode; see
[Agent teams](/cli/agent-teams) for the `/team` command.

### Language servers

When a session has language servers (the editor's in VS Code, servers the CLI
starts itself), the agent gets a read-only `code_intelligence` tool. It goes to a
definition or implementation, finds references, shows hover text, lists a file's
symbols, searches workspace symbols, and reports a file's current problems. The
agent names a position by file, line and the symbol on that line; the tool finds
the column. Results are capped at 50 entries. Without language servers the tool
is not offered. Switching the tool off (`CLINE_CODE_INTELLIGENCE_TOOL=0`,
`--no-code-intelligence-tool`, `codeIntelligenceTool: false`, or **Settings → Agent
Limits → Language servers** in VS Code) saves its tokens in every request; problems
after edits keep working.

After `editor` or `apply_patch` writes a file, the problems the edit introduced
are appended to the tool result:

```
New problems after this edit:
src/foo.ts
  12:5 error: Cannot find name 'bar'. [ts 2304]
```

A problem counts as new when the file did not already have one with the same
severity, message, source and code, so problems that only moved to another line
are not repeated. At most 20 are listed per file. When the language server fails
or does not answer in time, the edit still succeeds and nothing is appended.
`read_files` opens each file it reads in the language server, so the problems a
file already had are known before it is edited.

| Variable | Default | Governs |
|----------|---------|---------|
| `CLINE_LANGUAGE_SERVERS` | `true` | `false` (or `0`, `off`) keeps the CLI from starting language servers |
| `CLINE_CODE_INTELLIGENCE_TOOL` | `true` | `false` (or `0`, `off`) removes the `code_intelligence` tool but keeps the problems after edits |
| `CLINE_PROBLEMS_AFTER_EDIT` | `errors` | `errors`, `warnings` (errors and warnings) or `off` |
| `CLINE_PROBLEMS_TIMEOUT_MS` | `3000` | How long an edit waits for the problems to settle, in milliseconds |

The CLI takes `--no-language-servers`, `--no-code-intelligence-tool`,
`--problems-after-edit <off|errors|warnings>` and `--problems-timeout-ms <ms>`, and
reads `languageServers`, `codeIntelligenceTool`, `problemsAfterEdit` and
`problemsTimeoutMs` from `global-settings.json`. `languageServers` is an object:

```json
{
  "languageServers": {
    "enabled": true,
    "servers": {
      "go": { "command": ["gopls"], "extensions": [".go"] },
      "rust": false
    }
  }
}
```

Each `servers` entry gives the command that starts a server over stdio and the file
extensions it handles, plus optional `languageIds` (language id per extension),
`initializationOptions` and `startupTimeoutMs`. An entry named after a built-in
server replaces it, `false` turns it off, and a new name adds a server. The
`--language-servers` flags switch `enabled` and keep the configured servers. As
with the tool-call settings, an env var wins over the flag and the file, the flag
wins over the file, and values that are not valid are ignored.

#### Built-in servers

The CLI knows these servers and uses each one whose binary it finds in the
workspace's `node_modules/.bin` or on `PATH` when the session starts. When it finds
none, the session has no `code_intelligence` tool.

| Name | Files | Command | Install |
|------|-------|---------|---------|
| `typescript` | `.ts .tsx .mts .cts .js .jsx .mjs .cjs` | `typescript-language-server --stdio` | `npm i -g typescript-language-server typescript@6` |
| `python` | `.py .pyi` | `pyright-langserver --stdio`, else `basedpyright-langserver --stdio` | `npm i -g pyright` |
| `java` | `.java` | `jdtls -data <data dir>/jdtls/<workspace hash>` | [Eclipse JDT Language Server](https://github.com/eclipse-jdtls/eclipse.jdt.ls) |
| `go` | `.go` | `gopls` | `go install golang.org/x/tools/gopls@latest` |
| `rust` | `.rs` | `rust-analyzer` | `rustup component add rust-analyzer` |

`typescript-language-server` runs on the workspace's own `typescript` package when
it has one, otherwise on the one installed next to it. It needs TypeScript 6 or
earlier: TypeScript 7 has no `tsserver`. TypeScript 7 ships its own language server
instead, which you can configure in place of the built-in one:

```json
{
  "languageServers": {
    "servers": {
      "typescript": {
        "command": ["tsc", "--lsp", "--stdio"],
        "extensions": [".ts", ".tsx", ".mts", ".cts", ".js", ".jsx", ".mjs", ".cjs"]
      }
    }
  }
}
```

A server starts the first time a file it handles is read or queried, and gets 20
seconds to start (60 for `jdtls`; set `startupTimeoutMs` to change it). Sessions in
the same process share servers, and a server stays up for two minutes after the
last session using it ends, so the next session starts warm. A server that crashes
is not restarted until a new session starts.

### Compaction

When the conversation nears the model's context window, Cline summarizes the older
history and keeps the most recent part verbatim. In the VS Code extension these
settings are under **Settings → Agent Limits → Compaction** and apply when
auto-compaction is on under Features:

| Setting | Default | Governs |
|---------|---------|---------|
| **Compact at** | 90% | Share of the context window, as the provider counts tokens, at which compaction runs |
| **Keep recent context** | 60,000 tokens | Recent conversation kept verbatim, at most the size compaction shrinks the context to, so small context windows keep less |
| **Summary input per block** | 8,000 characters | How much of each tool result, file and thinking block the summarizer reads; the rest of a block is cut |
| **Summary length** | 8,192 tokens | Output cap for the summary. Until you change it, a Max Output Tokens set in the provider settings applies instead |

The last three apply to the agentic strategy, the default. In the SDK they are the
`compaction` fields `triggerRatio`, `preserveRecentTokens`, `summaryBlockChars` and
`summaryMaxOutputTokens`. The CLI has no flags or env vars for them.

### Fork build: no remote services

This build talks only to the providers, MCP servers and tools you configure.
Environment variables set when Cline runs cannot turn any of the following back
on.

**Telemetry.** PostHog usage and error reporting, feature flags, OpenTelemetry
export (including `OTEL_*`, `CLINE_OTEL_*` and organization remote config) and
Langfuse tracing are all off, and the device ID is a random value stored locally
instead of the machine ID. The telemetry setting is hidden.

**Cline services.**

- The Cline and ClinePass providers are not listed. A stored `cline` or
  `cline-pass` selection fails with "The Cline provider is not available in this
  build". With nothing configured, the default provider is OpenAI Compatible.
- There is no Cline sign-in, account view, credit or spend-limit message, or
  ClinePass promotion. Onboarding goes straight to configuring your own provider.
- Organization remote config, banners, cloud sessions and Composio connectors
  are off.
- Model metadata comes from the catalog bundled with the build: nothing is
  fetched from `models.dev` or Cline's recommended-models list. Model lists from
  your own provider (OpenAI-compatible `/models`, Ollama, LM Studio, or a provider
  you have a key for) still load.
- The marketplace catalog is not fetched, and official plugin names
  (`cline plugin install <name>`) are refused. Plugins from git, npm or a local
  path install as usual, and installed plugins, skills and MCP servers keep
  working.
- The CLI never checks for updates, and `cline update` prints "Updates are
  disabled in this build."
- The webview's Content Security Policy allows no outbound connections.

To build with upstream's behaviour, set `CLINE_REMOTE_SERVICES=on` when building
the extension or the CLI.
